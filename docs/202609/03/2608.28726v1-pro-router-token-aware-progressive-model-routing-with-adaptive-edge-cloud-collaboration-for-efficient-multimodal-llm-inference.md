## 摘要
多模态大语言模型（MLLMs）的卓越性能以巨大的计算开销为代价，给实时部署和成本效益带来了重大挑战。现有的模型路由方法要么仅基于粗略的请求级特征进行决策，要么花费一次或多次额外的语言模型传递来检查生成的响应，从而忽略了生成过程中出现的令牌级不确定性信号。为解决这些局限性，我们提出了Pro-Router，一种令牌感知的渐进式模型路由方法，采用自适应边云协作实现高效的多模态大模型推理。Pro-Router采用了两阶段渐进式决策机制。首先，轻量级提示预评分器模块在令牌生成开始前执行快速预筛选，将明显简单的请求引导至小模型。其次，令牌感知验证器读取小模型生成的每个令牌的采样概率分布，估计模型对其自身输出的置信度，以针对每个请求决定答案是直接返回还是升级到基于云的高精度模型。此外，我们设计了一种自适应边云服务流水线，该流水线根据每个设备测量的服务速率来调整每次调度的请求量，从而在不进行手动参数调整的情况下，使边缘和云端两层均保持充分利用，且不受网络延迟的影响。在多个多模态基准数据集和模型上进行的大量实验证明了Pro-Router的有效性。与其他方法相比，它实现了最高的路由准确性，并将路由速度提高了10倍以上。其服务流水线的端到端吞吐量也比现有的模型路由流水线高出75%以上。我们的代码可在https://github.com/xinyuangui2/pro-router获取。

## Abstract
The remarkable performance of multimodal large language models (MLLMs) comes at the cost of substantial computational overhead, posing significant challenges to real-time deployment and cost effectiveness. Existing model routing approaches either decide from coarse request-level features alone or spend one or several extra language model passes to inspect the generated response, leaving the token-level uncertainty signals that emerge during generation unused. To address these limitations, we propose Pro-Router, a token-aware progressive model routing method with adaptive edge-cloud collaboration for efficient multimodal LLM inference. Pro-Router employs a two-stage progressive decision mechanism. First, a lightweight prompt pre-scorer module performs rapid pre-screening before token generation begins, guiding apparently simple requests to small models. Second, a token-aware verifier reads the sampling probability distribution of each token the small model generates, estimating the model's confidence in its own output to determine, per request, whether the answer ships or escalates to the cloud-based high-precision model. Furthermore, we design an adaptive edge-cloud serving pipeline that sizes every dispatch to each device's measured service rate, so both the edge and the cloud tiers stay fully utilized without manual parameter tuning and are not impacted by the network latency. Extensive experiments on multiple multimodal benchmark datasets and models demonstrate the effectiveness of Pro-Router. Compared to other methods, it achieves the highest routing accuracy and improves routing speed by more than 10x. Its serving pipeline also reaches more than 75% higher end-to-end throughput than the existing model routing pipeline. Our code is available at https://github.com/xinyuangui2/pro-router.

## 1. 论文的核心问题与整体含义

论文聚焦于多模态大语言模型（MLLM）推理成本过高的问题。MLLM 虽然能力强大，但参数量大、自回归解码计算密集，单张图像还会产生大量视觉 token，放大 prefill 与 KV-cache 开销，因此生产环境中通常只能部署在昂贵的云端 GPU 上。然而，实际流量中大量请求并不需要最强模型，可以由小一个数量级的多模态小语言模型（MSLM）完成，这类小模型可以部署在更便宜的边缘设备上。

现有模型路由方法存在两类关键缺陷：

- **仅基于请求的路由（request-only）**：只在生成前根据请求本身做决策，成本低但准确性差，因为请求本身难以反映小模型能否真正作答。
- **基于响应的路由（response-based）**：等小模型生成答案后再用另一个语言模型或多次额外前向/生成来判断答案是否可信，信息量更大但额外开销极大，抵消了路由节省的成本。

论文还指出，已有的边云协作管线中边缘与云端频繁交互、相互等待，网络抖动会造成 GPU 空转。

**整体核心思路**：利用小模型解码时本来就产生的“token 级采样概率分布”作为不确定性信号，在几乎零额外开销下做出更准确的“直接返回（ship）或升级到云端大模型（escalate）”决策，并配合自适应边云调度管线保持两端设备高利用率。

## 2. 论文提出的方法论

### 2.1 总体框架：Pro-Router

Pro-Router 采用两阶段渐进式路由，流程为：输入请求 → 第一阶段预评分器 → 边缘小模型生成 → 第二阶段 token 感知验证器 → 决定返回还是升级到云端大模型。

### 2.2 路由目标的数学建模

论文构造了一个增益函数：

- 云端有 \(N_c\) 台设备，容量为 \(L_i\)；边缘有 \(N_e\) 台设备，容量为 \(S_j\)。
- 实际可用比例由 \(\eta_{L_i}, \eta_{S_j}\) 表示。
- 定义“ship rate”为 \(s = Pr[p \ge \tau]\)，即验证器接受小模型回答的概率；定义条件准确率 \(a = Pr[correct | p \ge \tau]\)；错误直接返回的回答有惩罚系数 \(\lambda\)。

总增益实质上取决于两个方向：更高的 ship rate 和更高的路由准确率。前者要求在生成前把简单请求送到小模型、难请求直接送大模型；后者要求最终决策模块本身足够准确，需要生成后才能得到的证据。这构成了渐进式路由的动机。

### 2.3 第一阶段：轻量级提示预评分器（Prompt Pre-scorer）

- 它不运行额外语言模型，也不占用 GPU。
- 使用三个廉价特征：**TF-IDF 向量**、**图像数量**、**提示长度**。
  - TF-IDF 捕捉问题风格和领域词汇带来的难度特征；
  - 图像数量作为多模态难度代理；
  - 提示长度弥补 TF-IDF 归一化丢失的长度信息。
- 输入经过训练好的**逻辑回归**，输出难度分数 \(p_{pre}(x) = \sigma(w^T \phi(x)+b)\)。

预评分器只负责“引导流量”而不是最终决策，简单请求从排序缓冲区的“易端”送入边缘小模型，困难请求从“难端”送入云端。

### 2.4 第二阶段：Token 感知验证器（Token-Aware Verifier）

关键思想：小模型每次解码都会输出一个词表概率分布，这个分布本身体现了模型对当前 token 的置信度。过去方法把这个信号丢弃，再花钱用另一个模型去重新评估；Pro-Router 则直接读取该信号。

对每个生成的 token \(t\)，提取四个特征：

- 生成 token 的对数概率：\(\ell_t = \log p_t(y_t)\)
- 最大概率：\(m_t = \max_v p_t(v)\)
- Top-K（K=20）概率质量的负熵：\(h_t = -H_t\)
- 位置比例：\(\rho_t = t/T\)

将这些特征堆叠为 \(X \in \mathbb{R}^{T \times 4}\)，输入一个带位置编码的 Transformer encoder，在序列维度上建模不确定性轨迹，再经平均池化+ sigmoid 输出一个置信度分数，决定“直接返回”还是“升级到云端”。

该模块只有约 6.7 万参数，完全运行在边缘设备的 CPU 上，不抢 GPU 计算资源，延迟仅约 2–3 ms。

### 2.5 自适应边云协作服务管线

论文分析了朴素管线吞吐量受限于：

\[
\Lambda \le \sum_i \mu_i^{edge} + \min\left(\sum_j \mu_j^{cloud}, \frac{N_c}{R+1/\bar{\mu}^{cloud}}\right)
\]

即边缘先跑、云端后接的模式使网络 RTT 进入关键路径，容易让部分设备空转。

Pro-Router 的全局调度器（Algorithm 1）采用闭式反馈控制：

- 按固定时间窗口 \(T_w\) 调度；
- 维护设备吞吐量的指数滑动平均（EMA）：
  \[
  \bar{\mu}_i^{(t)} \leftarrow \alpha \mu_i^{(t-1)} + (1-\alpha)\bar{\mu}_i^{(t-1)}
  \]
- 根据设备实际服务速率计算每次分派请求数：
  \[
  n_i = \lceil T_w \bar{\mu}_i \rceil + B_i
  \]
- 每个设备本地有缓冲区，并设置 KV-cache 利用率阈值与 backpressure 标志，避免过载和抢占；
- 分派规则：
  - 边缘 MSLM 取队列中难度最低的请求；
  - 云端 MLLM 优先处理升级缓冲区中的请求，再从输入缓冲区中取难度最高的请求；
  - 在线调整窗口大小 \(T_w\) 以适应网络 RTT 和集群吞吐量。

这样两端每台设备都能在其工作量时间内获得足够请求，避免因等待网络而空转。

## 6. 论文的主要结论与发现

- **Token 级不确定性信号是高价值路由依据**：小模型解码时自带的采样概率分布在计算上接近免费，但比文本表面特征、额外自验证甚至大模型回答都快且更准。
- **两阶段渐进路由是好设计**：生成前用轻量预评分器引导流量提升 ship rate，生成后用 token 感知验证器提升最终准确率，二者在不同时刻解决不同目标。
- **路由决策开销可以做到几乎可忽略**：本文验证器约 67k 参数在 CPU 上运行，将路由耗时的量级从“秒”级降到“毫秒”级。
- **自适应批量调度优于朴素顺序串联**：按测量吞吐量给每台设备分配“恰够一个时间窗”的请求数，可以避免 RTT 进入关键路径，显著提升边云混合集群的利用率。
- **该系统具有较好的鲁棒性和可扩展性**：在 1000 ms 量级网络延迟下仍保持 90% 以上吞吐，并扩展到多台边/云设备而不出现饱和拐点。
- **消融实验支持方法设计的必要性**：采样分布特征优于 3584 维隐藏状态；2 层 Transformer 优于量化摘要 + MLP；批式分派和 KV-cache 准入控制二者都是吞吐/延迟的关键组件。

## 7. 优点

### 方法上的亮点

1. **“零额外”信息读取**：利用解码时已有的概率分布做验证，没有引入新的语言模型前向或自回归生成，设计非常符合成本效益。
2. **时序轨迹建模**：通过 Transformer 对整个解码置信度轨迹建模，而非只是平均/汇总，能捕捉回答中间某段持续低置信度的信号。
3. **两阶段分工合理**：预评分器只做快速分流，不承担最终判定；最终判定交给信息更完整的 token 级验证器，做到速度与准确率兼顾。
4. **CPU/GPU 解耦**：验证器放在 CPU，不抢占 GPU，不拖慢小模型批量解码，实际上提升了整机可用吞吐。
5. **调度闭环与自适配**：EMA 吞吐跟踪、时间窗批量分派、缓冲区 backpressure 和 KV-cache 门控，形成一个无需手工调参的边云协作系统。

### 实验上的亮点

- 评测覆盖多种模态、两个标签体系（正确性标签与成对标签），结果一致性增强可信度；
- 报告了详细的路由延迟对比和吞吐对比，清晰揭示“路由信号开销”对端到端性能的量化影响；
- 消融实验针对输入特征、模型结构、管线设计三方面逐项验证，定位清晰的贡献来源。

## 8. 不足与局限

### 验证范围与偏差风险

1. **时间/资源信息不透明**：未报告总训练成本、训练数据来源、验证器训练轮数、逻辑回归训练细节等，作为系统论文可复现性受限制。
2. **高延迟下的路由决策新鲜度未验证**：当请求在缓冲区和反馈链路中等待较长时间时，模型已用真实吞吐率作出判断，但路由决策依赖的置信度阈值是否仍然合适没有被检验。
3. **“单一池化验证器”跨域泛化的挑战**：论文只在一个验证器覆盖全部 15 个基准的设定下工作。实际中出现全新领域时，验证器是否需要在线适应没有深入讨论。
4. **数学/长链推理的分析不足**：虽然包含 MathVerse、MathVision、GSM8K 等数学任务，但没有给出按任务类别的详细准确率分解；对带 CoT 输出的长序列不确定性轨迹是否有特殊优势，数据展示不够。
5. **“升级后云端答案”的影响**：文中没有明确分析“升云再生成一遍”对用户体验的额外延迟成本，也没有与缓存式级联（如重复使用边缘已生成前缀）这类优化进行对比。
6. **方法依赖采样概率分布**：如果推理引擎在部署时不返回 token 级分布或使用贪婪解码输出、仅保留 logprob，则该信号不一定可用；论文没有讨论兼容性与工程限制。
7. **未来发表/可核查性问题**：论文日期标注为 2026 年且部分参考文献较新，读者在复现时需注意版本一致性；文内未提供完整超参与环境配置说明。
