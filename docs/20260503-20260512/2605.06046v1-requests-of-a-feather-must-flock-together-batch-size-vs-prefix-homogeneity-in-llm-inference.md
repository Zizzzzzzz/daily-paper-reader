## 摘要
大语言模型中的自回归 Token 生成受限于内存，因为它需要“注意力机制”处理所有先前 Token 的键值张量（KV 缓存）。先前的研究旨在通过将多个请求批处理在一起，并在 GPU 显存限制下最大化批大小，来提高该解码过程的效率。本研究的关键观察是，在具有前缀共享的工作负载中，较小的、前缀同质的批次（即所有请求共享一个公共前缀）可以比更大的、异质的批次实现更高的解码吞吐量，这是由于 KV 缓存访问期间具有更好的空间和时间局部性。然而，最先进推理引擎中的前缀感知调度器仅为了减少 KV 缓存内存占用而最大化批次内的前缀重用，但并未在可能表现更好的较小同质批次处停止批次形成。此外，我们表明现有调度器中的共享前缀检测依赖于基数树（radix-tree）遍历，从而产生了巨大的 CPU 开销，通常与 GPU 执行时间相当。本文提出了 Feather，这是一种前缀感知调度器，它使用强化学习（RL）来学习批大小与前缀同质性之间的最佳权衡。我们还引入了分块哈希树（CHT），这是一种轻量级数据结构，可为 RL 调度器实现快速前缀检测和高效请求选择，从而避免昂贵的树遍历。我们将 Feather 集成到 vLLM 和 SGLang 中，评估结果表明，与现有调度器相比，Feather 实现了 2–10 倍的端到端吞吐量提升，同时在工作负载没有足够前缀共享时，其表现也不逊于现状。Feather 通过减少 KV 缓存访问的总数来实现这些增益，超越了具有相同目标的前缀感知注意力内核的性能。

## Abstract
Auto-regressive token generation in large language models is memory-bound because it requires "attending to" key and value tensors (KV cache) of all previous tokens. Prior work aims to improve the efficiency of this decode process by batching multiple requests together, and maximizing batch size subject to GPU memory constraints. The key observation of our work is that with prefix-sharing workloads, smaller, prefix-homogeneous batches -- where all requests share a common prefix -- can achieve higher decode throughput than larger, heterogeneous batches, due to better spatial and temporal locality during KV cache accesses. However, prefix-aware schedulers in state-of-the-art inference engines maximize prefix reuse within a batch only to reduce KV cache memory footprint, but do not stop batch formation at smaller homogeneous batches that could have performed better. Further, we show that shared prefix detection in existing schedulers relies on radix-tree traversals, incurring substantial CPU overhead that is often comparable to GPU execution time. This paper presents Feather, a prefix-aware scheduler that uses reinforcement learning (RL) to learn the optimal tradeoff between batch size and prefix homogeneity. We also introduce Chunked Hash Tree (CHT), a lightweight data structure that enables fast prefix detection and efficient request selection for the RL scheduler, avoiding expensive tree traversals. We integrate Feather into vLLM and SGLang, and our evaluation shows that Feather achieves 2--10$\times$ higher end-to-end throughput as compared to existing schedulers, while doing no worse than the status quo when the workload does not have enough prefix sharing. Feather achieves these gains by reducing the total number of KV cache accesses, surpassing the performance of prefix-aware attention kernels that have the same goal.

*   **研究动机**：现有的推理引擎（如 vLLM, SGLang）通常追求最大化批处理大小（Batch Size）以提高吞吐量。然而，作者发现对于存在前缀共享（如 Few-shot、RAG、系统提示词）的负载，**前缀同质性（Prefix Homogeneity）**——即批次内请求共享公共前缀的程度——对性能的影响甚至超过了批次大小。
*   **核心矛盾**：大批次往往意味着更高的异质性（不同请求前缀不同），这会破坏 GPU 显存访问的局部性；而现有的前缀感知调度器在检测共享前缀时存在巨大的 CPU 计算开销，甚至抵消了 GPU 的加速效果。

### 2. 方法论：核心思想与关键技术
作者提出了 **Feather** 调度器，包含两个核心组件：
*   **分块哈希树（Chunked Hash Tree, CHT）**：
    *   **核心思想**：放弃传统的逐 Token 基数树（Radix Tree）遍历，改用固定大小块（Chunk）的累积哈希。
    *   **技术细节**：将请求表示为哈希向量，利用反向索引和**最小堆（Min-Heap）**维护每个待处理请求的“缺失块计数”。这使得选择与当前批次最匹配的请求复杂度从 $O(W \times T)$ 降至 $O(\log W)$（$W$ 为等待队列长度，$T$ 为序列长度）。
*   **基于强化学习（RL）的调度策略**：
    *   **核心思想**：将“是否继续向当前批次添加请求”建模为一个决策问题，在“增加批次大小（提升利用率）”与“保持前缀同质性（提升访存局部性）”之间寻找最优平衡。
    *   **算法流程**：调度器观察当前批次大小、前缀损失量、等待请求数等特征，通过 Contextual Bandit 或 Q-Learning 算法决定是 `Add`（继续添加）还是 `Stop`（立即派发 GPU 执行）。奖励函数（Reward）直接设定为解码吞吐量。

### 6. 主要结论与发现
*   **局部性胜过批大小**：在长前缀场景下，一个由 100 个完全同质请求组成的批次，其吞吐量可能远高于 500 个异质请求组成的批次。
*   **CPU 开销不可忽视**：传统基数树调度器在处理长序列时，CPU 调度耗时竟能占到总延迟的 50%-90%，成为新的瓶颈。
*   **硬件无关性**：Feather 通过调度层优化访存局部性，其效果优于或等同于需要针对特定硬件精调的底层算子优化（如 PAT）。
*   **性能提升**：在存在前缀共享的情况下，Feather 实现了 **2-10 倍**的吞吐量提升，且显著降低了 Token 间的延迟（TBT）。

### 7. 优点
*   **视角独特**：首次系统性地揭示了批次大小与前缀同质性之间的权衡关系。
*   **架构轻量**：CHT 数据结构极大地降低了调度算法的复杂度，解决了长序列推理中的 CPU 瓶颈。
*   **自适应强**：引入 RL 使得调度器能根据实时负载和硬件环境自动调整策略，无需人工调参。
*   **易于集成**：作为调度层优化，可以无缝集成到 vLLM 和 SGLang 等主流框架中。

### 8. 不足与局限
*   **应用限制**：该方法的核心增益依赖于“前缀共享”，对于完全随机、无重复前缀的短文本对话负载，提升有限。
*   **多级前缀复杂性**：虽然文中测试了多级基数树，但在极其复杂的动态前缀树（如树状搜索解码）场景下，CHT 的分块哈希可能会引入微小的匹配精度损失（相比于 Token 级匹配）。
*   **分布式扩展**：目前实验主要集中在单 GPU 环境，尚未深入探讨在多 GPU 张量并行（TP）或流水线并行（PP）下的调度协调挑战。
